# 协同编码管线 · 架构与技术要点

> 本文档是 `pipeline/` 可执行实现的完整设计说明。
> 架构源头：Multi-Agent 仓库 `multi-agent-pipeline` skill（默认协同架构），2026-08-15 视觉位由 Kimi K3 更换为 Qwen3.8-Max（成本指令）。
> 流程图见 `../docs/coding_pipeline_flow.png`（纸墨风）。

---

## 1. 设计目标与边界

一句话：**用四个不同模型家族的模型，按各自长板分工，把「需求 → 可运行代码 + 视觉验证通过的页面」流水线化。**

三条原则（不可掺入的机制）：

1. **原始四角色，不加机制**：管线只有「设计 → 编码 → 审查 → 集成」四个环节。没有门禁层、没有仲裁层、没有校准阶梯——那些是数模管线的机制，编码管线不引入（2026-08-15 用户明确纠正）。
2. **写评分离**：写代码的 Kimi 不审查自己的代码；GLM 设计 + 审查，Qwen 视觉设计 + 视觉审查。
3. **Solo 逃生口优先**：管线不是默认选项。用户催/急、单文件 <50 行、CRUD 3-5 文件、单行修复 → 直接 solo，不跑管线。

## 2. 架构总览

### 2.1 四模型分工

| 角色 | 模型 | 职责 | API 端点 |
|---|---|---|---|
| 编排者 | DeepSeek V4 Pro | 理解需求 · 派发调度 · 汇总修复 · 集成验证 | `api.deepseek.com/chat/completions` |
| 设计者/审查者 | GLM 5.2 | 整体架构设计（文件清单+逐文件规格）+ 代码审查 | `open.bigmodel.cn/api/paas/v4` |
| 编码者 | Kimi K2.7 Code | 逐文件编写完整代码 | `api.moonshot.cn/v1` |
| 视觉/UI | Qwen3.8-Max | 视觉与 UI 设计 + 视觉产出审查（截图级） | `dashscope.aliyuncs.com/compatible-mode/v1` |

### 2.3 数据流契约

所有中间产物落盘在 `<项目>/pipeline_artifacts/`，每个阶段只读上游文件、只写自己的产物：

| 文件 | 生产者 | 消费者 | 格式 |
|---|---|---|---|
| `requirements.md` | Phase 0 DeepSeek | Phase 1a/1b、Phase 4 | 固定小节 + `VISUAL: yes/no` 行 |
| `design.md` | Phase 1a GLM | Phase 1b/2/3a | `### FILE:` 块协议（见 §4.2） |
| `visual_spec.md` | Phase 1b Qwen | Phase 3b | 页面清单/视觉规格/检查清单 |
| `review_code.md` | Phase 3a GLM | Phase 4 | 每文件一节，`✅ 通过` 或 `⚠️ 需修改` |
| `review_visual.md` | Phase 3b Qwen | Phase 4 | 同上 |
| `final_report.md` | Phase 4 DeepSeek | 人 | 交付物/审查摘要/验证状态/残留风险 |

## 3. 视觉环节的触发与实现

### 3.1 触发判定（Phase 0）

DeepSeek 在 requirements 中输出一行 `VISUAL: yes|no`。判定依据：交付物是否含 HTML/CSS/SVG/图表生成代码/图片。

- `no` → Phase 1b 与 Phase 3b 整体跳过（纯后端/CLI 项目不付视觉调用成本）
- `yes` → 视觉设计 + 视觉审查全开

### 3.2 视觉审查的文件类型路由

| 文件类型 | 审查方式 |
|---|---|
| `.html` / `.svg` | playwright（chromium headless）以 `file://` 加载渲染 → 截图 → 送 Qwen |
| `.png` / `.jpg` / `.webp` | 直接作为图像输入送 Qwen |
| `.css` / `.scss` | 不单独审——随页面截图一并覆盖；纯样式文件在报告中注明 |
| 后端代码 | 不送视觉审查 |

### 3.3 截图与图像处理细节

1. playwright 加载静态页面（无服务器依赖，`file://` 协议），等待 600ms 让 JS 渲染完成；
2. PIL 压缩：宽度 >1280px 缩至 1280，转 JPEG quality 72——控制图像输入体积，避免 API 请求过大被拒；
3. 图像以 base64 data URL 放进 `messages[].content[]` 的 `image_url` 字段（OpenAI 兼容格式，DashScope compatible-mode 接受）。

## 4. 关键技术要点

### 4.1 四模型 API 实测特性（llm_client.py）

| 模型 | 实测特性 | 客户端处理 |
|---|---|---|
| `deepseek-v4-pro` | 推理模型；支持 `reasoning_effort`（none~max） | Phase 0/4 编排任务用 `high` |
| `glm-5.2` | **推理模型：`reasoning_content` 消耗 max_tokens 预算**——预算过小时 `content` 返回空串 | 设计 64K、审查 8K 预算 |
| `kimi-k2.7-code` | **推理型 coder：同上**，reasoning 吃预算；API 仅允许 `temperature=1` | 编码 32K 预算、强制 temperature=1 |
| `qwen3.8-max` | 支持图像输入（多模态）；DashScope compatible-mode | 图像走 base64 data URL |

> ⚠️ 模型 ID 教训：仓库旧文档曾写 `kimi-k2.7-coder`，实测 `/v1/models` 端点 404——正确 ID 是 `kimi-k2.7-code`（另有 `kimi-k2.7-code-highspeed` 变体未实测）。模型 ID 一律以 `/models` 端点实测为准，禁止凭文档写。

### 4.2 GLM 设计文档解析协议

GLM 被要求输出严格格式，管线用正则解析：

```markdown
### FILE: <相对路径>
职责：一句话
依赖: <本文件依赖的其他文件路径，逗号分隔；无依赖写 无>
规格：<完整规格——做什么/接口/关键逻辑/输入输出/注意事项>
```

解析规则：

1. 按 `### FILE:` 分块，路径取块内首行；
2. `依赖:` 行提取依赖列表，Phase 2 按依赖顺序编排写入（依赖文件先写，其内容摘要注入编码 prompt）；
3. 相邻文件之间的 `## GROUP` 标记 = 这些文件相互独立，Phase 2 用 `ThreadPoolExecutor` 并行编写；
4. 无 GROUP 标记时全部串行（安全优先）。

**路径安全**：文件路径必须相对、禁止 `..`，落盘前 `os.path.normpath` 后断言仍在项目目录内——防 GLM 输出异常路径越界写盘。

### 4.3 Kimi 逐文件编码的上下文控制

每个文件的编码调用只注入三样东西（控制上下文与成本）：

1. 该文件在 design.md 中的规格；
2. 其 `依赖:` 声明的文件内容（截断 4000 字符/文件）；
3. 输出约束：只输出完整代码，无解释、无 markdown 围栏（围栏残留会被 `strip_fences` 剥掉）。

这是原始架构「Do NOT give Kimi the entire spec at once」原则的实现。

### 4.4 审查 → 修复闭环（Phase 4）

1. 从两份审查报告里按文件名正则切节，找 `⚠️` 且不含 `✅ 通过` 的文件；
2. 每个被标记文件：DeepSeek 拿「当前内容 + 问题清单」重写完整文件，覆盖落盘；
3. 修复只跑一轮——不无限循环，剩余问题写进 final_report 的「残留风险」。

### 4.5 可靠性与重试

- `ask()` 对网络错误与空/过短输出自动重试 2 次，指数退避（8s/16s）；
- `min_chars=4` 阈值：兼容「✅ 通过」这类短输出，低于阈值视为失败重试；
- 各阶段产物先落盘再进下一阶段——任一阶段中断后可从中断处产物恢复，不用重跑前序。

### 4.6 密钥与环境

加载顺序：`os.environ` > `pipeline/.env` > 当前目录 `.env`（后两者已 gitignore）。

```
DEEPSEEK_API_KEY / GLM_API_KEY / KIMI_API_KEY / QWEN_API_KEY
KIMI_BASE_URL（可选，默认 https://api.moonshot.cn/v1）
```

## 5. 成本控制要点

| 手段 | 说明 |
|---|---|
| 视觉环节条件触发 | `VISUAL: no` 时省掉 Phase 1b/3b 的全部视觉调用 |
| 逐文件最小上下文 | Kimi 编码只注入规格 + 依赖摘要，不注入全量设计文档 |
| 审查短输出检测 | 4 字符「✅ 通过」不触发重试（不浪费重试预算） |
| 单轮修复 | 修复循环最多一轮，不无限重写 |
| Solo 边界 | 小任务直接不启动管线 |

## 6. 已知边界（诚实声明）

1. **审查深度受限于单次调用**：GLM 代码审查对语义级 bug（如 `>` 与 `>=` 的边界差）可能漏检并输出「✅ 通过」。管线不内置确定性检查层（按「原始架构不加机制」原则），此类漏检依赖 Phase 3b 视觉审查与 Phase 4 修复环节兜底。
2. **设计阶段无算术核验**：GLM 设计文档中的数字性内容（示例数据、期望结果）无独立复算，错误会沿规格传播。
3. **静态页面优先**：视觉审查基于 `file://` 静态渲染；需要后端服务的项目（API 返回数据）截图环节需要外部先把服务跑起来。
4. **修复环节不验证编译**：Phase 4 重写文件后不自动执行测试/编译（遵循原始架构边界）。
